# 터미널 협업·활동 기록·자체 호스팅 경쟁 조사

조사일: 2026-10-29. 범위: 제품의 실제 기능과 설명을 공식 자료에서 확인하고, 공개 이슈·사용자 의견으로 진입·운영의 마찰을 보완했다. 반복 동기와 Terminal World(TW)의 기회는 자료에 기반한 **분석 가설**이며 사용률·수요의 증거는 아니다. 제품 개별 기능은 서비스 및 버전에 따라 바뀔 수 있다. 아래 ‘한계’는 명시된 기술적 경계와 분석상 적합성 한계를 구분한다. TW는 현재 기획과 비교하며 구현 여부를 전제하지 않는다.

## 1. sshx — 브라우저 기반 터미널 공유

- **대상과 문제:** 원격 디버깅·교육 등에서 상대에게 실제 터미널을 빠르게 보여주고 함께 사용하려는 개발자. 한 명은 터미널에서 시작하고 상대는 초대 링크를 브라우저에서 연다.
- **기능 및 근거(공식):** 하나의 링크로 다중 터미널, 커서 및 실시간 채팅; 종단간 암호화와 재연결 기능. [제품 홈페이지](https://sshx.io/), [공식 README](https://github.com/ekzhang/sshx). v0.3.0부터 별도의 **읽기 전용 링크**가 도입되었다. [릴리스 노트](https://github.com/ekzhang/sshx/releases).
- **반복 동기(추론):** 개발 작업 중 설명하기 어려운 상태나 오류를 다른 사람과 직접 볼 때 재사용할 동기가 있다. 혼자서 활동을 정리하거나 내일 작업을 이어가는 지속적 목적은 이 제품의 중심 효용이 아니다.
- **경계와 TW 기회:** 즉시 공유 및 관찰은 이미 구현돼 있다. 따라서 ‘터미널 기반 페어링’이나 ‘관찰 모드’ 단독으로는 차별적이라고 할 수 없다. 공식 README는 자체 호스팅 배포를 현재 지원하지 않으며 실제 배포는 TLS·프록시·네트워킹 등 운영 구성이 필요하다고 밝힌다. [README](https://github.com/ekzhang/sshx). 신뢰할 수 있는 소규모 집단 안에서 무엇을 공유할지 선택하고 작업의 맥락을 남기는 흐름은 검증할 수 있는 기회 가설이다. 단, sshx에 유사 기능이 절대 없다는 뜻은 아니다.

## 2. tmate — tmux 기반 즉석 페어링

- **대상과 문제:** 같은 터미널 세션을 보며 진단하거나 작업하려는 사용자.
- **기능 및 근거(공식):** tmux의 포크로 즉시 페어링을 제공한다. 공개 서버는 **2025년 7월 종료**되었으며 현재 기본 설정만으로 작동하지 않는다. 서버 재작성·호스팅 복구를 추적 중이고 자체 서버 구성은 가능하다. [프로젝트 README](https://github.com/tmate-io/tmate), [복구 추적 이슈 #336](https://github.com/tmate-io/tmate/issues/336).
- **반복 동기(추론):** 서버 장애·환경 재현·페어링 요청이 발생할 때 쓰는 사건 기반 도구다. 주기적인 개인 작업 정리 자체가 핵심은 아니다.
- **경계와 TW 기회:** 자체 서버 운영 능력이 필요하고 호스팅 서비스 의존의 실제 지속 가능성 문제가 드러난다. [이슈 #322](https://github.com/tmate-io/tmate/issues/322)는 원격 현장의 연결 실패를 보고했으며, 전체 서비스의 현재 가동률을 측정한 것은 아니다. TW가 실시간 공유를 MVP로 넣는다면 무심코 외부 서비스의 지속 가능성을 전제하지 말고, 공유를 선택 기능으로 분리할 필요가 있다(분석).

## 3. Zellij — 일상 터미널 작업공간 + 협업

- **대상과 문제:** 터미널에서 창과 세션을 관리하며 기존 작업 맥락을 이어가거나 필요시 공유하고 싶은 개발자.
- **기능 및 근거(공식):** 패널·세션과 프로젝트별 레이아웃, 브라우저 클라이언트, 자체 웹 서버 인증 및 읽기 전용 토큰을 제공한다. [기능 설명](https://zellij.dev/features/), [웹 클라이언트 문서](https://zellij.dev/documentation/web-client.html), [FAQ](https://zellij.dev/faq/). 웹 서버는 기본적으로 꺼져 있으며 비로컬 인터페이스에는 HTTPS 인증서가 필요하다. 인증된 일반 사용자는 신뢰된 것으로 취급한다.
- **반복 동기(추론):** 동료 접속 여부와 상관없는 개인 세션·레이아웃이 일상의 사용 이유가 된다. 공유는 필요할 때 추가되는 효용이다.
- **경계와 TW 기회:** Zellij는 이미 솔로 효용, 실시간 공유 및 읽기 전용을 모두 다룬다. ‘혼자서도 쓸 수 있는 터미널’만으로 경쟁 우위가 성립하지 않는다. 자체 서버 운영에는 인증서와 노출 설정이 수반된다. 호스팅 서비스 Zellij.online은 공식 설명 기준 유료·무료 계층이 있는 **비공개 베타**다. [운영 설명](https://zellij.dev/zellij-online/). TW가 구체적 작업 전후의 맥락 복원 또는 스터디 피드백 문제를 짧은 흐름으로 해결하는지는 별도 인터뷰가 필요한 가설이다.

## 4. Visual Studio Live Share — IDE 내 실시간 공동 개발

- **대상과 문제:** 코드, 오류, 실행 환경을 함께 보고 디버깅하거나 멘토링하려는 개발자·팀.
- **기능 및 근거(공식):** Visual Studio 및 VS Code를 중심으로 공동 편집·디버깅·터미널·로컬 서버를 공유한다. 참여자가 저장소 복제나 SDK 설치를 미리 할 필요가 없다고 설명한다. [Microsoft FAQ](https://learn.microsoft.com/en-us/visualstudio/liveshare/faq), [제품 설명](https://visualstudio.microsoft.com/services/live-share/). 읽기 전용 설정이 있고 공유된 터미널이나 디버깅 REPL은 명령 실행 위험이 있어 신뢰하는 사람과 사용하도록 경고한다. [보안 문서](https://learn.microsoft.com/en-ca/visualstudio/liveshare/reference/security).
- **반복 동기(추론):** 코드 리뷰·버그 해결·교육 중 즉시 같은 맥락을 볼 때 재사용한다. 이런 필요가 매일 발생한다는 근거는 아니다.
- **경계와 TW 기회:** 문서상 주요 지원 도구가 Visual Studio와 VS Code이므로 다른 작업 환경 사용자는 해당 도구를 도입해야 할 수 있다. 한 사용자의 [이슈 #5053](https://github.com/microsoft/live-share/issues/5053)은 팀원에 따라 링크가 가입되지 않는 경험을 보고했다. 이를 모든 사용자의 현재 문제로 일반화할 수는 없다. Terminal World의 터미널 인터페이스는 에디터 선택과 무관한 가벼운 작업 기록에 유리할 수 있으나, IDE의 협업 기능과 동등한 개발 역량을 제공한다고 가정해서는 안 된다.

## 5. WakaTime — 자동 개발 활동 기록

- **대상과 문제:** 자신 또는 팀의 코딩 시간·프로젝트별 분포를 수동 타이머 없이 이해하려는 개발자.
- **기능 및 근거(공식):** 에디터 플러그인의 활동 이벤트를 시간 구간으로 처리하고 개인 및 팀 대시보드·목표·프로젝트별 통계를 제공한다. 소스 코드 본문은 보내지 않지만 파일 경로·프로젝트·브랜치 등 메타데이터는 처리한다고 밝힌다. [기능 설명](https://wakatime.com/features), [FAQ](https://wakatime.com/faq).
- **반복 동기(추론):** 작업에 수반된 자동 수집과 회고용 대시보드는 사용자의 단독 사용 및 정기 확인을 가능하게 한다.
- **경계와 TW 기회:** 기록량은 맥락·문제 해결의 질과 같지 않다. FAQ는 편집기별 감지 이벤트와 입력 시간 제한에 따라 읽기·휴식 시간이 처리되는 방식이 달라질 수 있다고 설명한다. ‘데이터 기반 생산성’ 주장을 신중하게 다뤄야 한다. 사용자가 명시적으로 작성한 다음 행동·막힌 지점만 보관하고 필요한 상대에게만 공유하는 접근은 검증 가능한 차별 가설이다. 시간 측정 자체의 차별성은 이미 낮다.

## 6. ActivityWatch — 로컬 중심 자동 활동 기록

- **대상과 문제:** 기기의 앱·웹사이트 사용과 시간 분포를 프라이버시를 고려해 파악하려는 개인.
- **기능 및 근거(공식):** 오픈소스 자동 기록, 앱·창 제목, 카테고리, 브라우저 및 에디터 확장과 로컬 데이터 보관을 제공한다. [공식 홈페이지](https://activitywatch.net/). 다만 v0.14부터 사용자가 선택적으로 외부 AI 요약을 호출하면 일부 데이터가 선택한 제공자에게 전달될 수 있다. [프라이버시 정책](https://docs.activitywatch.net/en/latest/privacy.html).
- **반복 동기(추론):** 백그라운드 수집이 쌓인 기록을 다시 살펴볼 이유를 만든다. 개인만 사용할 때도 가치가 발생한다.
- **경계와 TW 기회:** 자동 감지는 설치 및 기록 범위에 대한 신뢰가 필요하며 활동량이 작업의 목적과 막힌 이유를 설명하지는 않는다(분석). 2026-10-06 공식 동기화 글은 다기기 동기화를 선택적으로 수동 설정하고 일부 범위와 삭제 전파에 제약이 있다고 설명한다. [동기화 안내](https://activitywatch.net/blog/syncing-your-activitywatch-devices/). 동일 날짜 출시 글은 v0.14를 설명하지만 [다운로드 페이지](https://activitywatch.net/downloads/)에는 더 이전 버전이 안정판으로 표시되어 공식 페이지 간 표시가 일치하지 않아 버전 상태는 재확인이 필요하다. 수집 없이 사용자가 통제하는 명시적 작업 맥락 기록은 별도 수요 검증이 필요한 기회다.

## 7. Zulip — 주제별 비동기 대화와 self-hosting

- **대상과 문제:** 소규모 팀, 연구실, 오픈소스 등에서 여러 대화를 맥락을 유지하며 비동기로 따라잡고 싶은 집단.
- **기능 및 근거(공식):** 주제별 대화를 분리·검색하며 자체 호스팅과 데이터 내보내기를 제공한다. [공식 Slack 비교](https://docs.zulip.com/slack-alternative/), [오픈소스 커뮤니티용 설명](https://albert.zulip.com/for/open-source/). 운영 문서는 전용 기기 또는 VM, 2 GB RAM 이상, DNS 및 메일 설정 등을 요구한다(문서의 12.1 버전 기준). [프로덕션 요구사항](https://zulip.readthedocs.io/en/12.1/production/requirements.html).
- **반복 동기(추론):** 지속되는 팀 대화·질문·결정과 기록 검색이 재방문을 만든다. 구성원이 활발하지 않으면 채팅의 즉각적 가치는 줄어든다.
- **경계와 TW 기회:** 이미 검증된 조직형 비동기 커뮤니케이션과 자체 호스팅 대안이다. 범용 채팅을 다시 만드는 경쟁보다 작업 기록을 팀에 **선택적으로** 전달하고 나머지 대화는 기존 도구에 남기는 흐름이 유용할지 검증할 수 있다. 이는 미충족 수요의 실증이 아니다.

## 실제 사용자의 공개 반응 및 해석 한계

1. [r/devops, 협업 코딩 도구 경험 토론](https://www.reddit.com/r/devops/comments/1mqelpz/does_anyone_actually_use_collaborative_coding/)에서 게시자는 Live Share가 빠른 디버깅에는 괜찮았지만 일상의 관행으로 정착하지 않았다고 설명했다. 다른 댓글은 화면 공유와 대화를 선호했고, 또 다른 댓글은 각자 다른 위치의 코드를 보거나 함께 편집하는 유연성을 긍정했다. **상반된 개별 의견이며 실제 사용률이나 전체 개발자 선호도는 알 수 없다.**
2. [r/webdev, 시간 추적 웹앱 개발 경험](https://www.reddit.com/r/webdev/comments/101idpa/i_made_a_time_tracking_webapp/)에서 한 작성자는 회사 노트북에 활동 추적 앱을 설치하는 것이 부담스러워 대안을 만들었다고 밝히며, 브라우저 환경에서 자동 추적에 제약이 있다고 설명했다. **개인 사례이자 작성자의 자기 보고**이며 일반적인 기업 정책이나 자동 추적 전체의 문제를 입증하지 않는다.
3. [sshx 사용자 권한 요청 #72](https://github.com/ekzhang/sshx/issues/72)는 참여자별 다른 권한에 대한 구체적 요청이다. 프로젝트의 [v0.3.0 릴리스 노트](https://github.com/ekzhang/sshx/releases)는 그 후 읽기 전용 모드의 도입을 설명한다. 이는 기능이 이제 없다는 증거가 아니라, **관찰·입력 권한 구분이 실제 요청되었고 이미 경쟁 제품에 반영된 사례**다.
4. [tmate 이슈 #322](https://github.com/tmate-io/tmate/issues/322)는 2025년 한 사용자가 원격 장비로 접속하지 못했다고 보고한다. 시스템 가용성 측정이나 현재 모든 사용자 상태로 일반화할 수 없다. README의 공개 서버 종료 사실은 별도의 공식 출처로 확인했다.

## 합성: 제품 탐색에 유효한 제약

- 개인에게 당장 도움이 되는 흐름이 반복 사용의 발판이 될 수 있지만, 기존 Zellij·ActivityWatch·WakaTime도 개인 효용을 제공하므로 **혼자 사용 가능만으로는 부족**하다.
- 사람의 도움이 필요한 순간 자체를 제거하기보다 작업을 시작·중단·재개하고 도움을 요청하는 맥락을 간결하게 남기는 것이 차별화 가설이 될 수 있다. 여기서 맥락을 작성하는 부담과 기존 메모·GitHub 이슈·메신저 대비 이점은 반드시 비교 실험해야 한다.
- 실시간 공동 터미널 기능은 이미 여러 제품이 제공하며, 이는 권한·명령 실행·인증·운영이라는 비용을 수반한다. 동기 협업을 기본 가치나 매일 사용할 것으로 가정하지 않는다.
- ‘사용자가 적으면 가치가 없다’는 상태를 완화하는 것은 제품 설계 원칙이지 사용자 수요가 검증됐다는 뜻이 아니다. 실제 모집 대상과 인터뷰, 대조군 사용 및 재방문 관찰이 별도로 필요하다.
