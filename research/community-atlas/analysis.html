현재 기획의 진짜 약점

01 · 참여 계약

들어오면 무엇이 달라지는가?

로비·카페·옥상은 장소 이름이다. 누구에게 무엇을 제공하고 무엇을 돌려받는지 설명하지 못한다. “개발자끼리 교류”는 너무 넓다.

02 · 수요와 공급

질문자·제작자만으로는 부족하다

답할 사람과 체험할 사람이 필요하다. 비동기는 동시접속 부담을 줄이지만 무응답 문제를 해결하지 않는다.

03 · 축적

채팅 밖에 무엇이 남는가?

같이 만든 결과물, 서로를 이해한 맥락, 이후의 역할이 없다면 재방문 이유도 약하다. 시간 랭킹은 이를 대신하지 못한다.

타당한 우려와 지나친 전제 · 실제 구현 상태

타당: SSH와 감성만으로 기존 관계망을 이길 이유가 약하다. 기능이 많아지면 초기 인원과 운영자의 관심이 분산된다. SSH에 들어간다고 로컬 작업 맥락이 자동 연결되지도 않는다.

수정할 전제: 모든 커뮤니티가 혼자서 완전한 가치를 줄 필요는 없다. 기존 소수 집단과 구체적 활동으로 시작할 수 있다. 즐거움·소속감·창작도 실제 가치다. 생산성 효과로 억지 번역할 필요는 없다. 다만 사람이 없는 순간에는 작품과 기록이 남아 있어야 한다.

구현 사실: 현재 src/cli.tsx:60–78은 macOS 로컬 TUI, 로비·RoofTop·개인 공간과 고정 예시 사용자를 명시한다. 실제 원격 전달·SSH·다중 사용자 통신은 제공 약속이 아니다. docs/requirements-analysis.md는 SSH 다중 사용자 서비스의 요구사항이며 임의 셸·코드 실행·호스팅은 기본 범위에서 제외한다. 이 연구의 새 기능을 구현 완료로 읽으면 안 된다.

기존 코드와 과제의 확정 문서는 보존했다. 자유 실행을 채택한다면 요구사항과 보안 경계를 따로 개정해야 한다.

03 · WHAT ACTUALLY TRANSFERS

화면 대신
사람 사이의 교환 구조를 가져온다.

동일한 댓글도 작품 평가·공동 연구·수령 약속에서 다른 가치를 만든다. 아래 연결은 해석이며 Terminal World의 효과 검증 결과가 아니다.

공동 소유

내가 만든 것이 이곳의 일부가 된다

tilde.town 공용 제작 공간은 개인 홈을 넘어 공동 프로젝트를 관리한다. 현대 MOO도 주민이 객체와 행동을 바꾸는 구조다.

이식: 프로필 장식 밖으로 나와 주민의 작품을 공용 놀이·도구로 채택한다. 원작·변형·관리자를 기록한다.

조건: 쓸 사람부터 확보한다. 모두 편집 가능하다는 기능만으로 공동 소유가 완성되지는 않는다.

실제 관객

좋아요보다 체험이 돌아온다

Show HN은 직접 써볼 수 있는 작품을 요구한다. itch.io 잼에는 제출·평가 단계가 있으며 공식 문서는 인기 편향과 투표 조작을 경고한다.

이식: “어땠어요?”보다 “어디에서 막혔나요?”를 묻는다. 체험→개선→재체험을 연결한다.

조건: 제작자만 모집하지 않는다. 의무를 채우는 형식적 댓글은 성공이 아니다.

주기와 축적

정해진 활동이 다음 기록을 만든다

Friday Postcards는 주간 수집 활동이다. aNONradio에는 회원 진행자와 편성·기록이 있다.

이식: 한 회의 제작→체험→후기→다음 회의 수정작. 종료 후에도 작품을 열어본다.

조건: 출석 강요 대신 참여할 이유를 제공한다. 주제 공급과 진행자가 없으면 일정만 남는다.

검토되는 증거

작은 기여가 공동 지식에 들어간다

iNaturalist 식별, Zooniverse 자료별 토론, OSM 검증은 대화와 검토 대상을 연결한다.

이식: 실험 조건·출력·한계를 남기고 다른 환경의 결과를 연결한다.

조건: 검토 노동을 숨기지 않는다. “미확인”도 정상 상태이며 인기와 정확성을 분리한다.

역할과 관계

함께한 이력이 사람을 연결한다

Recurse 사회 규칙은 배우는 관계의 행동을 구체화한다. Discworld MUD에는 길드·상점·신문 같은 역할이 있다.

이식: 체험자·큐레이터·진행자·관리 역할을 실제 기여와 연결한다.

조건: 뱃지와 위계보다 책임 범위가 먼저다. 동의 없는 코드 지적과 지나친 간섭을 제한한다.

발견 가능한 문화

작은 취향이 선택 이유가 된다

Lobsters는 주제를 좁힌다. Tildes는 예측 가능한 탐색을 지향한다. Neocities는 개인 창작 공간의 발견을 돕는다.

이식: 모든 개발자 대신 작은 텍스트 작품을 만들고 구경하는 취향을 모은다. 최신·미응답·관심 주제를 제공한다.

조건: SSH가 좋은 사람을 자동으로 선별하지 않는다. 작은 집단도 신고·차단·운영 설명이 필요하다.

반례: 창작·참여가 늘어도 가치가 줄 수 있다
  • iNaturalist 사용자 토론: 행사 후 검토자 부담에 대한 우려. 기여량과 품질은 다르다.
  • Exercism 공식 문서: 사람 피드백은 시간이 걸릴 수 있다. 검토자를 무료 기능처럼 취급하지 않는다.
  • tilde.town 운영 기록: 자원 고갈과 예방적 보안 중단. 무료 셸 공급과 공동체 가치를 구별한다.
  • cohost 종료 회고: 독특한 문화가 운영 지속을 보장하지 않는다. 졸업 후 유지와 내보내기를 정한다.

개별 사례는 문제의 존재를 보여줄 뿐 빈도·대표성·인과적 유지율을 입증하지 않는다.

점수를 높게 준다고 수요가 증명되지 않는다. 같은 기준과 실패 조건으로 비교하고, 이번에는 전략적 우선순위를 제시한다.

1순위 · 제작과 관객

작품 제작회 → 창작 마을

내 작품이 다른 사람에게 체험되고 그 반응으로 다음 작품이 달라진다. 원래 공간·개인 정체성을 살리면서 함께 만드는 대상을 제공한다.

2순위 · 공동 발견

터미널 기술 탐험대

같은 기술 질문을 각자 실험하고 환경 차이와 결과를 합친다. 실용성과 학습이 분명하지만 과제·검토자가 병목이다.

3순위 · 공동 서사

비동기 추리·텍스트극

타인의 단서와 선택 때문에 내가 쓴 이야기와 세계가 바뀐다. 공동 놀이가 목적이며 지속적인 집필이 필요하다.

9 / 9개 아이디어

변경 범위는 기존 커뮤니티와의 관계에 대한 분류다. 난이도는 본문에 적힌 최소 소프트웨어 구현 범위 기준이며, 운영 노동·자유 코드 실행은 별도다. ‘목적 변경’ 후보는 전면 변경에 포함했다.

어느 방향도 Terminal World 수요를 입증하지 못했다. 1순위는 현재 공간·정체성과 연결되고 작은 실험이 가능한 전략적 선택이다. 모두에 1~5점을 붙여 합산하면 서로 다른 불확실성이 가려지므로 이번에는 수치 순위를 사용하지 않았다.

세 가지 수준의 전략: 유지 / 중심 변경 / 전면 피벗

기존 유지: 기존 친구들의 사교 공간은 가능하나 채팅·집중·게시판 추가만으로 외부 사용자 이동을 설명하기 어렵다. 낮은 구현 변화, 높은 기존 관계 의존.

중심 가치 변경 — 권고: 개인 공간과 커뮤니티를 살리고 함께 만드는 대상·관객·반응을 중심에 둔다. 핵심 변화는 활동과 운영 계약이다. 새 기능만으로 차별화됐다고 보지 않는다.

전면 피벗: 범용 생산성 도구·자유 셸 호스팅·완전한 RPG는 지금 즉시 선택하지 않는다. 반면 SSH 때문에 체험이 끊기면 웹 체험과 TUI 제작을 병행하는 인터페이스 변경은 허용한다. 커뮤니티의 교환이 먼저다.

05 / RECOMMENDED, NOT VALIDATED

작품을 구경하러 와서,
세계의 일부를 만드는 주민으로

Terminal World를 ‘터미널의 작은 창작물을 함께 만들고 체험하는 커뮤니티’로 검증한다. 첫 제품은 거대한 마을이 아니라 약 10명이 여는 작은 제작회다.

검증 전 추천

작품 → 체험 → 반응 → 수정 → 재체험의 관계를 만든다. 장기적으로 회원이 방·이야기·사물을 만드는 마을로 확장하되, 작은 교환의 반복부터 검증한다.

누구를 먼저 모을 것인가

기존 대학 개발 동아리·취미 집단의 텍스트 게임·ANSI·작은 CLI 제작자와 체험을 즐기는 관객이다. 개발자 전체를 타깃으로 삼지 않는다.

제작자: 내 작품을 실제로 써 보고 무엇이 달라졌는지 말해 줄 사람이 필요하다.
관객: 설치 부담 없이 체험하고 허용된 작은 변형으로 제작에 참여하고 싶다.

새롭다고 주장할 수 없는 부분

itch.io의 제작·제출·평가 구조, Discord 모임, tilde.town의 공동 프로젝트, mooR의 공동 공간 제작이 이미 있다.

차별성 가설발견 → 즉시 체험 → 허용된 변형 → 원작자와 후속 교류가 기존 조합보다 덜 번거로운지가 승부처다. SSH나 방 이름 자체는 경쟁 우위가 아니다.

왜 이 사용자부터인가? 대상별 JTBD 비교

JTBD는 사용자가 특정 상황에서 이루려는 일이다. 기존 동아리를 먼저 택한 이유는 접근·관찰 가능성이며, 가장 강한 시장 수요가 확인됐기 때문은 아니다. 아래 반복 가능성은 가설이다.

집단·상황이루려는 일 / 기존 대안장벽·반복 가능성 / 판단
텍스트 작품을 만드는 대학 동아리원작은 작품을 끝내고 실제 반응을 받기 / Discord·itch.io·동아리 발표관객 부족·SSH 설정. 후속 작품과 수정이 있을 때 반복 / 첫 관찰 집단

오픈소스 기여자·유지관리자기여를 검토받고 반영하기 / GitHub Issues·PR실제 저장소·검토자가 필요 / 파트너 확보 전 제외
원격 협업·집중 목적 개발자업무 공동 편집·집중 / Live Share·tmate·Focusmate보안·통합·네트워크 효과 경쟁 / 초기 대상에서 제외

첫 5분과 다음 주의 경험

  1. 발견·첫 접속: 제작회 초대로 들어와 사람과 샘플 3개, 이용법과 변형 허용 범위를 확인한다.
  2. 첫 가치: 짧은 분기 이야기를 체험하고, 허용된 대사 한 줄이나 결말을 바꾼다. 미리보기 후 원작자·부모 버전 출처를 유지해 게시한다. 누군가 구체적으로 반응해야 사회적 경험이 완성된다.
  3. 재방문: 제작자는 “두 번째 선택지가 헷갈렸다”는 반응을 보고 수정한다. 관객은 자신의 제안이 반영된 버전을 다시 체험한다. 다음 주제와 변형본이 일주일 뒤 복귀할 이유다.

Trigger → Action → Value → Return

새 작품·내 제안의 수정본 발견 → 짧게 체험하고 한 가지 반응 또는 변형 남기기 → 내 기여가 타인의 작품에 반영됨 → 답변·다음 버전·다음 제작회로 복귀. 접속 보상 대신 서로의 결과물이 다음 행동을 만든다.

BEFORE / 지금의 기획

사람들이 정해진 방으로 이동한다

로비에서 접속자를 보고, 옥상에서 대화하고, 집중방에서 시간을 잰다. 콘텐츠와 기능은 주로 운영자가 공급한다.

AFTER / 검증할 장기 모습

주민의 작품이 방문할 공간이 된다

내가 만든 짧은 미로에 이웃이 새 길을 붙이고, 그 변형본의 결말을 보러 다른 사람이 찾아온다. 작품의 저자·함께 바꾼 사람·변경 기록이 공간의 정체성이 된다.

가치 가설“이곳에 내 작품을 기다리고 함께 바꾸는 사람이 있다.” 이 관계가 없다면 공간 구현만 늘리지 않는다.

누가 누구에게 왜 응답하는가

제작자는 작품마다 “이번에 확인하고 싶은 질문 하나”를 적고, 관객은 관심 작품을 골라 한 번 체험한다. 제작자는 수정 여부와 이유를 답한다. 의무 평가나 빈 칭찬 교환을 요구하지 않는다. 미응답 작품은 운영자가 조기에 발견하되, 운영자의 반응은 별도 기록한다.

운영 시점제공과 수요를 맞추는 활동
월~목운영자가 샘플 3개 준비, 제작자가 체험 가능한 최소 버전과 질문 게시
금요일 45분첫 10분 발견·체험, 다음 20분 반응·변형, 마지막 15분 원작자 응답과 다음 수정 약속
주말~다음 회비동기 수정·재체험. 운영자 재촉 없이 누가 다시 오는지 관찰
추천을 뒤집을 수 있는 반론과 대응
  • 관객이 없다: 작품 공급만으로 커뮤니티가 생기지 않는다. 체험자의 과업과 즐거움을 먼저 확인하고, 확보되지 않으면 오픈 플랫폼을 만들지 않는다.
  • 행사가 끝나면 떠난다: 행사를 즐긴 것과 지속 관계를 구분한다. 다음 회 자발 복귀와 동일 작품의 후속 교환으로 판단한다.
  • tilde나 itch.io의 복제다: 기존 도구로 충분하면 모임만 운영하고 별도 플랫폼 개발을 중단한다.
  • 안전한 템플릿이 창작을 제한한다: 초기 실험은 제한된 텍스트 창작의 수요만 검증한다. 자유 코딩·임의 실행 수요를 검증한 것으로 확대 해석하지 않는다.
  • 제작보다 함께 탐험하는 수요가 강하다: 같은 조건의 실험을 수행하고 차이를 공유하는 ‘탐험대’ 후보로 전환한다. 다른 가설이므로 새 행동 실험이 필요하다.

06 / OPERATE FIRST, BUILD AFTER EVIDENCE

최소 커뮤니티부터 운영하고,
검증된 마찰만 제품으로 만든다

아래는 제품 설계 제안이다. 실제 기능 구현이나 자유 코드 실행을 제공하지 않는다.

개발 전 MVP: 기존 도구 + 작품 3개

기존 itch.io·Discord 또는 집단이 쓰는 도구에서 초대, 작품 목록, 체험, 반응, 수정본 링크를 운영한다. 선언적 분기 이야기·ANSI 작품·간단한 입력 반응 작품을 샘플로 준비한다. 계정·SSH 설정 때문에 첫 체험이 막히는지도 기록한다.

구현 Gate 이후의 최소 제품

작품 목록·즉시 체험·허용 범위가 표시된 변형·미리보기·출처 유지 게시·버전/부모 관계·작품별 질문과 댓글을 구현한다. 체험 이벤트는 최소한으로 기록하고, 신고·차단·게시 변경 되돌리기·데이터 내보내기를 포함한다.

유지·변경·폐기

유지

터미널의 텍스트 표현, 연결된 공간의 감각, 로비에서 사람과 새 작품을 발견하는 경험. 익숙한 TypeScript·Ink의 입력·화면 구성 패턴.

변경

방은 기능 메뉴에서 작품·공동 프로젝트의 맥락으로 바꾼다. 개인 공간은 작품과 기여의 기록으로, 게시판은 작품별 후속 교환으로 좁힌다.

폐기·유보

집중 랭킹·출석·잠수방·일반 IT 뉴스 수집·범용 게시판·초기 페어 프로그래밍·전면 AI 생성·대규모 월드 장식. 실시간 자유 채팅은 핵심 교환이 생긴 뒤 보조로 검토한다.

SSH 클라이언트 → 강제 TUI 앱 ─┐
                             ├→ 동일 HTTPS API → 권한·작품/버전 서비스 → PostgreSQL
웹 읽기 화면 ────────────────┘              └→ 검토된 제한 체험 엔진
브라우저 체험: SSH 진입장벽 근거가 생기면 단계 2에서 검토

SSH 서버는 셸 대신 앱만 실행하고 인증된 계정에 권한을 매핑한다. 공동 상태와 권한 판정은 공용 서비스가 책임진다. 작품·버전·부모·동의·댓글·체험·신고를 별도 모델로 저장한다. 원본 버전은 보존하고 새 수정본을 만들며 충돌 시 명시적으로 재시도한다. 웹과 TUI는 같은 데이터·권한 규칙을 사용한다. 라이브러리 추가는 전제하지 않는다.

TUI 화면과 저장·통신의 구체적 경계
[작품 마당] 새 작품 / 미응답 / 내가 참여한 작품
  제목 · 원작자 · 체험 시간 · 확인하고 싶은 질문
         ↓ Enter
[체험] 제한 엔진의 텍스트·선택지 / 종료 / 신고
         ↓ 체험 종료
[작품 기록] 내 반응 / 저자 답변 / 변경점 / 허용된 변형
         ↓ 미리보기 → 게시
[새 버전] 원작·부모 버전·저작자·변형 허용 범위 보존

이 화면은 설계안이다. 첫 버전은 비동기 교환이므로 HTTPS 요청과 화면 진입·수동 새로고침으로 충분하다. 서버 이벤트 알림은 후속 교환을 놓치는 문제가 관측되면 SSE 등으로 추가한다. 공동 편집·실시간 채팅·WebSocket은 초기 필수가 아니다.

저장 API는 같은 게시 요청의 재시도를 중복 작품으로 만들지 않아야 한다. 게시 전 권한과 부모 버전을 검증하고, 같은 버전에 대한 동시 변경은 충돌로 반환한다. 테스트는 타인 작품 수정 거부, 허용되지 않은 변형 거부, 제어 문자 차단, 연결 단절 후 재시도, DB 백업 복구에 집중한다. 핵심 위험은 TUI 그림보다 다중 사용자 상태와 운영 복구다.

실행 경계·보안·기술적 깊이

MVP에서 임의 셸과 사용자가 올린 코드는 실행하지 않는다. 검토된 엔진이 선언적 텍스트 분기·검토된 템플릿만 해석하고 입력 길이·분기 수·실행 시간·출력량을 제한한다. 자유 CLI 호스팅은 범위 밖이다.

ANSI는 허용된 표현만 사용하고 OSC·클립보드·터미널 제어 이스케이프를 제거한다. 사용자별 데이터 접근을 서버에서 검사하고, SSH 키 등록·해지와 계정별 권한을 분리한다. 연결·저장량·체험 횟수 quota, 엔진과 API의 리소스 분리, 감사 기록과 신고 처리를 설계한다. 향후 임의 실행은 별도 샌드박스·격리·네트워크 제한을 요구하므로 자동 확장하지 않는다.

운영 중단에 대비해 작품·저작자·동의·부모 관계를 내보내고, 승계 시 동의·삭제 요청을 처리한다. 기술적 깊이는 버전 계보·권한·체험 엔진·동시 수정·장애 회복의 검증에 둔다. tilde.town의 자원 장애·제한 운영 기록은 공동체에도 운영 비용이 생김을 보여준다.

07 / BEHAVIOR BEFORE PLATFORM

“재미있다”보다,
서로의 다음 행동이 생기는가

가장 중요한 가설은 낯선 UI의 흥미가 아니라, 체험자의 반응이 제작자의 수정과 재체험을 실제로 만든다는 것이다.

인터뷰: 최근 행동을 묻는 다섯 질문

  1. 가장 최근 작은 작품을 만들거나 체험한 과정을 실제 링크와 함께 보여 달라.
  2. 누가 어떤 반응을 남겼고, 그 뒤 무엇을 바꾸었는가? 반응이 없었다면 어떻게 했는가?
  3. 남의 작품을 체험하다 설치·계정·규칙 때문에 멈춘 최근 사례는 무엇인가?
  4. 변형하거나 제안했던 내용이 반영된 뒤 다시 찾아갔는가? 기록이 남아 있는가?
  5. 다음 제작회에 실제 작품 또는 체험 시간을 낼 수 있는가? 기존 도구로 충분한 이유는 무엇인가?

1~2주: 운영 실험과 구현 착수 Gate

제작자 5명·관객 5명을 가정해 기존 도구와 샘플 3개로 서로 다른 두 관계에서 체험 → 구체적 반응 → 수정 → 재체험이 완료되는지 관찰한다. 운영자·친구의 요청에 따른 행동과 자발 행동을 구분하고, 다음 회에 스스로 돌아오는지 본다. 반응이 없거나 기존 도구로 충분하면 플랫폼 구현을 보류한다.

다음 실험: 두 집단, 교차 순서

두 소규모 집단이 기존 방식과 제한 프로토타입을 서로 다른 순서로 사용하게 한다. 난도가 비슷한 다른 작품을 쓰고, 발견·설치/접속·체험·게시·응답까지의 총시간과 운영자 개입 시간을 기록한다. 순서 효과를 줄이려는 설계이며 시장 수요로 일반화하지 않는다.

사전 운영 판단 기준의 예시

대상자·역할·교환 기회 수를 사전 정의한다. 첫 5분 체험·변형 성공, 교환 완성, 자발 복귀, 미응답 수, 총시간을 기록한다. 두 관계의 완성과 다음 회의 자발적 후속 교환은 개발을 검토할 최소 신호이며 통계적 유의성이나 산업 유지율 기준이 아니다. 참여 기회가 없으면 수요 실패로 단정하지 않는다. 다만 수정 실험은 한 번, 전체 4주 이내로 제한하고 여전히 판단할 자료가 없으면 구현을 보류한다.

지표의 분모와 운영자 개입 기록
  • 첫 사용: 실제 초대 수 → 접속 시도 수 → 5분 안에 도움 없이 한 작품 체험을 끝낸 수. 변형은 선택 과업으로 별도 기록한다. 접속 포기도 누락하지 않는다.
  • 교환 완성: 비운영자 사이에서 체험·구체적 반응·저자 수정·동일 체험자 재체험까지 이어진 관계 수와 해당 작품 수. 반응을 받을 기회가 있었던 전체 게시 작품 수를 함께 보고한다.
  • 복귀: 첫 주 활동자 중 다음 7일에 개인 재촉 없이 후속 행동한 사람 수 / 해당 첫 주 활동자 수. 제작자·체험자를 따로 집계하고 단순 로그인은 세지 않는다. 백분율과 실제 분자·분모를 함께 표시한다.
  • 공급 비용: 작품당 운영자 준비·모집·독촉·응답 시간, 무응답 작품 수, 대기 시간. 전체 일정 공지와 개인 독촉을 구분한다.
  • 비교 실험: 같은 과업의 성공·실패, 총시간, 운영 도움 횟수, 마지막에 사용자가 실제 선택한 방식. 작은 표본의 평균 차이를 인과적 효과로 단정하지 않는다.
판단관찰과 다음 행동
유지자발 교환이 반복되고, 기존 방식의 구체적 마찰이 확인되며 프로토타입이 총비용을 줄인다. 해당 부분만 구현한다.
수정제작자만 복귀하거나 관객만 소비한다. 작품 범위·질문·모임 시간·대상 집단 중 하나를 바꾸고 재실험한다.
중단반응과 복귀가 운영자 재촉에만 의존하거나 기존 도구로 충분하다. 별도 플랫폼 개발을 중단하고 필요하면 제작회만 유지한다.

개발 일정 가정: 3인·8주 구현 프로젝트는 사전 운영·재방문 검증을 통과한 뒤 시작한다. 1~2주차는 데이터·권한·체험 엔진, 3~4주차는 작품·버전·변형·댓글, 5~6주차는 격리·복구·웹 읽기·접근성, 7~8주차는 실제 제작회 파일럿과 결함 수정에 쓴다. 사전 실험 1~2주는 별도다. 총 8주라면 기능을 줄인다. 각자 데이터/API, TUI/체험, 운영/검증을 맡되 보안·교환 흐름은 함께 검수한다.

최종 다섯 질문에 대한 답
  1. 지금의 Terminal World를 쓸 이유가 충분한가? 현재 기획만으로는 부족하다. 기능과 공간의 결합이 반복 교환을 보장하지 않는다.
  2. 가장 심각한 문제는 무엇인가? 기능 수보다 누구와 어떤 결과물을 주고받으려는 제품인지 불명확한 것이 먼저다.
  3. 살릴 것인가, 중심 가치를 바꿀 것인가? 커뮤니티와 터미널 표현은 살리되 ‘접속해 머무는 곳’에서 ‘작품을 매개로 함께 바꾸는 곳’으로 중심을 좁힌다.
  4. 계속 쓰겠다고 느낄 첫 경험은? 내가 체험하고 바꾼 부분에 원작자가 답하고, 그 답이 다음 버전에 반영되어 다시 체험하는 순간이다.
  5. 졸업 프로젝트에서 합리적인 방향은? 기존 집단의 작은 제작회로 수요를 검증한 뒤, 제한 엔진·버전 계보·안전한 공동 상태를 갖춘 좁은 제품을 완성한다. 반복이 없으면 확대를 멈춘다.
